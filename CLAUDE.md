## What this is

**Nexstream Kansai Quest** — a single-page, no-build web app for a company trip to Kansai (28 Sep – 3 Oct 2026): a live Leaflet map of where colleagues are, a traveller's handbook, and a Party Games hub (scavenger hunt, landmark race, trivia). Plain HTML/CSS/JS with `<script>` tags. No npm, no bundler, no framework, no tests.

## Architecture

**One global scope, load order matters.** `index.html` holds all CSS, all markup, and a large inline `<script>` (~line 234–699) that defines everything the modules depend on: `sb()`, the `db` helpers, `me`, `players`, `esc()`, `haversine()`, `drawSprite()`, `SPOTS`, `DAYS`, the map, the handbook shell and the games shell. Modules load *after* it at the bottom of the file, each with a `?v=<stamp>` cache-buster — **bump that stamp on every deploy that touches a module**, or GitHub Pages and mobile Safari will keep serving the old file after `index.html` has updated, which looks exactly like the change never shipped. Load order:

```
art.js → checklist.js → handbook.js → game-hunt.js → game-race.js → game-trivia.js → game-sushi.js → chat.js
```

Nothing is a module in the ESM sense — every top-level `const`/`function` is a browser global.

**`route.js` is the one exception to "modules load after the inline block."** It is tagged right next to the Leaflet `<script>` near the top of `<head>`, before the inline block even starts, not down with the list above. The reason is the auto-rejoin path: a returning player (the common case — the name is remembered in `localStorage`) hits `if(saved&&saved.name){ ... startGame(true); }` at the very end of the inline block, and `startGame` calls `initMap()` immediately — while still inside that block, long before any bottom `<script src>` tag has had a chance to run. If `route.js` loaded down there like the others, `ROUTE_WALK` would be `undefined` at the moment `initMap()` needs it and the returning player would just never see the footpath ribbon, silently. Loading it early costs nothing (it's pure data, no dependencies) and side-steps the ordering hazard entirely.

**Game module contract.** The games shell (`gameShowTab`) looks up four functions on `window` by name and tolerates missing ones:

| Function | When it runs |
|---|---|
| `render<Name>()` | returns the tab's HTML string |
| `init<Name>()` | after the HTML is injected — wire events here |
| `tick<Name>()` | every 5s while the overlay is open |
| `stop<Name>()` | on tab switch or overlay close — clear timers/rAF here |

`<Name>` comes from `GAME_TABS` (`Hunt`, `Race`, `Trivia`, `Sushi`). **Every other top-level name in a module must be prefixed** — `hunt*`/`HUNT_`, `race*`/`RACE_`, `trivia*`/`TRIVIA_`, `ck*`, `route*`/`ROUTE_` — because there is no scope isolation. Adding a game means: new `game-*.js`, a `<script>` tag, and a `GAME_TABS` entry.

**Hunt claims need a photo, shot in Japan.** `CLAIM 📷` opens one shared hidden `<input type="file" accept="image/*" capture="environment">` — `capture` goes straight to the camera, so a picture from the camera roll (or from last year) cannot be passed off as proof. The button is also gated by `huntWhereAmI()`: a live GPS fix, no older than 10 minutes, inside the `HUNT_JAPAN` bounding box. A manual PIN explicitly does **not** count — it is self-declared, which would make the check pointless — so unlike `raceInRange()` the hunt does not honour `me.manual`. The reason is shown up front in the `#huntGeoNote` banner rather than only on tap, and re-checked when the shot comes back, since the camera can sit open for a while. The fix that let a claim through is written to the row's `lat`/`lng`. Note this makes claiming untestable outside Japan by design. The input is visually hidden but **laid out** — Safari will not open a picker for a programmatic `.click()` on a `display:none` input. It writes the claim through `huntClaim(ch, file)` rather than directly; `huntClaim(ch, file)` then shrinks, uploads and only writes the row once it has a URL, so a failed upload never leaves a proofless claim. Every claimant's proof shows as a thumbnail strip on the card, tap for a full-size lightbox appended to `<body>` (it has to clear the `z-index:900` games overlay). Thumbnails render with an empty `src` and a `data-path`; `huntSignProofs()` runs after each wire-up, batch-signs whatever is still blank in one request and fills the URLs in, caching them in `huntSigned` until a minute before expiry — otherwise the 5s `tickHunt()` re-render would re-sign every photo on screen every tick. Race claims are GPS-verified and take no photo.

**Handbook** renders through `TABS[].render()`; seven tabs, whose render functions live in `handbook.js` (`renderRules`, `renderTips`, `renderLang`, `renderMust`, `renderStay`, `renderPack`) except `renderItin` which is inline in index.html. `renderRules` is the group-trip rules tab — who the coordinators (the "person in charge") are, what must be reported to them and how fast, and conduct while moving as a company group; keep logistics on `renderStay` and Japanese etiquette on `renderLang` rather than duplicating them there. `renderLang` is the Japanese language-and-etiquette tab — phrases, the lines staff say back to you, signs, and the do/don't cards; it owns all of that content, so don't re-add phrases or etiquette to `renderTips`, which keeps the logistics only. Anything CJK in it needs the `.jp` class, because both `VT323` and `Press Start 2P` lack Japanese glyphs — keep kana and kanji out of headings entirely. `renderBook()` also calls `ckOnPackShown()` when the Pack tab is shown, which is how `checklist.js` hooks in.

**Sushi Roll rounds are started by a player, not the clock.** `game-sushi.js` opens on a lobby — everyone with the tab open, listed but not scoring — until someone taps START, which schedules the round `SUSHI_COUNT_MS` in the future and broadcasts it. `startAt`, that scheduled instant, *is* the round's identity: every phone folds it into a seed and derives the whole round — ingredient calls, the difficulty ramp, box-shuffle positions — from a PRNG keyed on that seed, so nothing about the round itself has to arrive on time once `startAt` is known. Because broadcast is lossy, `startAt` doesn't only ride the one-shot "start" message — it rides every periodic state ping too, so a phone that missed the start message picks the round up from the next ping. Two people tapping START at once resolve by earliest-`startAt`-wins, a rule every phone applies independently. Anyone who opens the tab after play has already begun spectates that round (watching, not scoring) and is auto-entered into the next one, rather than being dropped in mid-round with a head start nobody else got. The realtime topic name is versioned (`kansai-sushi-v2`) specifically so a phone still serving a cached pre-lobby build can't broadcast old clock-derived round state into a lobby-model room.

**Party chat** lives in `chat.js` (`chat*`/`CHAT_` prefixes). It polls `chat_messages` every 3s like reactions do and pops every incoming message twice: a speech balloon above the speaker's map marker (a throwaway Leaflet `divIcon` marker, same trick as `popReaction`) and a toast in `#chatPops` — a `position:fixed`, `z-index:1200` stack outside `#game`, so a message still shows while the games or handbook overlay is open. `chatStart()` is called from `startGame()`; because auto-rejoin runs before `chat.js` loads, the module also self-starts at the bottom of the file if `#game` is already `.on`. Sends are optimistic and reconciled when the row comes back from the server (`chatSettleMine`); a failed send stays in the log with a tap-to-retry line.

**Chats and reactions echo in the NEARBY tray.** `trayEchoSay()` / `trayEchoReact()` (inline, beside `renderTray()`) stamp a short-lived `trayEcho[player_id]` entry that `renderTray()` paints as a `.echo` bubble on the speaker's card — 8s for a chat line, 4s for a reaction. It is absolutely positioned over the bottom of the card's `.m` block — today that's the walk-distance row (`.wk`, see below), not the distance line above it — but the tray's height never moves mid-message regardless of what the echo happens to sit over, because that row is always present (`walkHtml()` reserves it even when empty) and `--trayh` never has to react to it. The hooks are `popReaction()` (one line covers both your own reaction and everyone else's) and, in `chat.js`, `chatPop()` for incoming plus `chatSend()` for your own line — `chatSettleMine()` deliberately has none, or your own message would echo twice. Two things fall out of `renderTray()` rebuilding every card on each poll and each GPS fix, i.e. about once a second while walking: it saves and restores `#cards`' `scrollLeft`, and `trayEchoHtml()` emits `animation:none` on any repaint later than `TRAY_ECHO_FRESH` after the echo was stamped, or the entrance animation replays and the bubble blinks for its whole lifetime. `trayEchoSay()` ignores a line older than its own lifetime, so the `CHAT_BACKLOG` history replayed on join does not land on cards as fresh speech; `chatPost()` calls `trayEchoClear()` when a send fails, so your card never claims a message went out while the log below says it did not.

**Overlay chrome is measured, not hardcoded.** `trackChrome()` (inline, called from `startGame()`) publishes the live heights of `#hud` and `#tray` as the `--hudh` / `--trayh` CSS vars on `:root`, via a `ResizeObserver` plus `resize`/`orientationchange`/`document.fonts.ready`. `#status` sits at `top:calc(var(--hudh) + 8px)` and `#sidebtns`/`#emojiPanel`/`#chatPanel` at `bottom:calc(var(--trayh) + 10px)`. Use those vars for anything new anchored to the top or bottom of the map — a fixed offset breaks as soon as the HUD wraps to two or three rows on a narrow phone, which is what used to bury the Games and Handbook buttons under the status box.

**Pixel art** is defined as arrays of character rows mapped through a palette (`ART_PAL`, `ICON_PAL`), rasterised to canvas once at load and cached as data URLs. `art('key', size)` returns an `<img>`; `ICON_URL[...]` holds the 8×8 map/itinerary icons. To add art, add rows to `ART16` in art.js — no image files.

**The route ribbon is walked footpath where it can be, straight dashed hop everywhere else.** `initMap()` walks the `order` array of `SPOTS` keys leg by leg; for each consecutive pair it looks the leg up in `ROUTE_WALK` (from `route.js`) and, on a hit, draws that leg's real pedestrian-path points solid instead of the plain two-point straight line. Everything without an entry — which is most of the route, since most of the trip is train, plane, or (for Rokko) ropeway — stays the old dashed straight hop. This split is deliberate, not cosmetic: dashed means "you get there roughly this way, but not on foot", solid means "this is the actual path you walk". The `ropeway → terrace` leg in particular must never gain an entry in `ROUTE_WALK` — it's a cable car over a mountain, and pedestrian-routed geometry for it would be a lie about how you get there. `route.js` is **generated, not hand-written** — see `tools/build-route.py` below — and `ROUTE_WALK` is guarded with `typeof` in `initMap()`, so if the file ever fails to load, every leg just falls back to a straight dashed hop, i.e. exactly the old behaviour, rather than breaking the map.

**Every leg is stroked three times, and the basemap is muted to let the result read.** A cream `#f3e8cf` casing at weight 10, a red `#c8442b` core at weight 5, then the gold `#c9a24a` ribbon at weight 3 on top. The casing and core are stroked **per group — transit and walked separately — never over both at once**, and that is not a style choice: a solid core running under the dashed gold overlay fills the dashes' gaps with red and a train hop ends up looking exactly like a walked path, destroying the distinction the paragraph above exists to make. The whole transit stack is therefore dashed (`dashArray:'10 14'`), with all three of its layers sharing that array and the `.routeflow` class so they stay in phase while the ants crawl, and `lineCap:'butt'` throughout — a round cap extends each dash by half the stroke weight at both ends, which on the weight-10 casing closes the very gaps the dashes need. Change the dash array and the `routeAnts` keyframe's `stroke-dashoffset` must change with it (it has to equal dash + gap, currently 24) or the loop stutters every repeat; the animation is gated on `prefers-reduced-motion:no-preference` like the ME marker's bob, which is safe because the dashes, not their movement, are what marks a leg as carried. The layering is also why `.leaflet-tile-pane` is filtered down to `saturate(.55)` from the old `saturate(1.35)`: a saturated basemap put OSM's own roads at the same weight and tone as the route and the line vanished into them. Treat the two as one decision — turning tile saturation back up, or thinning the casing, re-hides the route. All six polylines are `interactive:false` purely to skip hit-testing and `cursor:pointer` on long paths that have no popup or handler; it is **not** needed to keep map clicks working, since Leaflet's `_findEventTargets` only treats a layer as an event target when it actually listens for that event, so a handler-less path never consumes the map's own click.

**`tools/build-route.py` regenerates `route.js`.** It's a standalone, stdlib-only Python 3 script — re-run it with `python3 tools/build-route.py` whenever a `SPOTS` coordinate moves or a walking leg is added to its `WALK_LEGS` list (it reads `SPOTS` and the route `order` straight out of `index.html` by regex, so it can't drift out of sync with them). For each walking leg it calls the public Valhalla pedestrian-routing instance at `valhalla1.openstreetmap.de`, decodes the returned polyline6 shape, pins the endpoints to the exact `SPOTS` coordinates (Valhalla snaps to the nearest walkable way, which can land tens of metres off the marker), simplifies it with Douglas–Peucker, and sanity-checks the result (routed distance vs. straight-line, every point inside a Japan bounding box, every leg key genuinely consecutive in `order`) before writing `route.js` — it fails loudly rather than writing bad geometry. It needs network access to `valhalla1.openstreetmap.de` to run. Deliberately **not** OSRM: the public OSRM demo server ignores the routing profile and serves car geometry for every costing, which is actively wrong for pedestrian-only streets like Sannenzaka/Ninenzaka.

**Walking distance to another player is two-tier, and only one tier ever touches the network.** `renderTray()` and `renderMarkers()` repaint roughly once a second while walking (every 6s poll, every GPS fix), so the always-on number on a tray card has to be pure math: `walkEstimate()` is haversine distance inflated by a flat urban-detour factor (`WALK_DETOUR`, 1.3) and walked at an average pace (`WALK_KMH`, 4.8 km/h), capped at `WALK_MAX_KM` so a Kyoto/Osaka pair ~40km apart shows nothing rather than a meaningless "8h 20m walk". The real number — an actual pedestrian route from the same public Valhalla instance `tools/build-route.py` already calls — is fetched by `walkTap()` from exactly one place: a marker's `popupopen` handler, which a tray-card tap already triggers via `openPopup()`. That is a hard rule, not a convenience: a routing call inside either render function would fire on every poll instead of once per popup-open, and there is no fallback path that puts one there. The result is cached in `walkCache`, keyed by `walkKey()` — all four coordinates rounded to 4 decimal places (~11m) — so repeat taps on a stationary pair cost nothing and the cache self-invalidates the moment either person actually moves; a failed or timed-out call is remembered in `walkFail` so a down Valhalla instance isn't hammered on every tap, and a fresh tap aborts whatever request is still in flight (`walkAbort`) so two routes can never race to draw, with the abort checked against the live controller before being recorded as a failure so a merely-superseded request doesn't poison `walkFail` for a key that never actually failed. `walkDecodePolyline6()` decodes at precision 6 (divisor 1e6), mirroring `tools/build-route.py`'s `decode_polyline6()` exactly — Valhalla's `shape` is polyline6, not the far more common polyline5, and decoding at the wrong divisor silently produces points off by about ten degrees rather than throwing. The routed line itself (`walkDraw()`) reuses the trip ribbon's cream-casing/red-core stack but deliberately drops the gold top layer: gold is what marks a line as *the* itinerary route in `initMap()`, and this line means "your walk to one person right now" — giving it the same gold would make it look like it belongs to a route it has nothing to do with.

## Data layer (Supabase PostgREST)

All persistence goes through `sb(path, opts)` in index.html — raw REST against `/rest/v1/`, with the project URL and **anon key hardcoded in index.html**. RLS is deliberately open to `anon` for every table: anyone with the link can read and write. That is an accepted tradeoff for a private trip game — do not store anything sensitive.

**`sb()` returns `null` for empty response bodies.** Writes send `Prefer: return=minimal`, which PostgREST answers with 201/204 and no body. Write code must not expect JSON back. (An earlier version only special-cased 204 and called `r.json()` on 201's empty body, throwing `JSON.parse: unexpected end of data` — which made optimistic UI updates roll back even though the row was saved.) `sb()` still throws on any non-OK status, which is what the offline/rollback paths in the game modules key off.

Tables (see `supabase-setup.sql`):

- **`players`** — one upsert-by-`id` row per person; position pushed every 30s, all players pulled every 6s. Rows older than `STALE_MS` (3h) are filtered out client-side.
- **`reactions`** — append-only emoji pops, polled every 3s, no client update/delete.
- **`quest_claims`** — shared by four features, split by `kind`: `'hunt'`, `'race'`, `'pack'` (the personal pack checklist, only ever queried filtered to your own `player_id`). Unique on `(player_id, kind, target)`, so writes are upserts with `?on_conflict=player_id,kind,target` + `Prefer: resolution=merge-duplicates`. `proof_path`, `lat` and `lng` are set by hunt claims only; they are null on race and pack rows and on hunt claims made before photo proof existed.
- **`trivia_answers`** — unique on `(player_id, q_id)`; one active question per 30min derived from the clock, not from server state.
- **`arcade_scores`** — append-only (`game='deerdash'`); anon has select+insert only. **Orphaned on purpose:** the Arcade game (Deer Dash) was dropped from the app, so nothing writes here any more. The table, its rows and its RLS policies are left in place deliberately — `supabase-setup.sql` is a record of migrations already applied, not a script to re-run, so dropping the table would falsify that record.
- **`chat_messages`** — append-only party chat, polled every 3s by `chat.js`; anon has select+insert only, with a `char_length(body) between 1 and 240` check. `lat`/`lng` are captured at send time so the map balloon can be placed even if the sender has since moved.

**Storage.** One **private** bucket, `proofs`, holds the scavenger-hunt photos under `hunt/<challenge>/<player>-<ts>.jpg`. Anon may insert and select, never update or delete, so a proof cannot be swapped out once posted. Uploads do **not** go through `sb()` — Storage is a different API — they use `sbUpload(bucket, path, blob)`, which returns the **object path**; `sbSign(bucket, paths, ttl)` batch-mints 1-hour signed URLs for reading. Both are in index.html. Pair uploads with `shrinkImage(file)`, which canvas-downscales a phone photo to a 1280px JPEG (a 3000×2000 shot lands around 50 KB); a raw 8 MB camera file would otherwise blow past the bucket's 5 MB ceiling. Unclaiming deletes the row but leaves the file — anon has no delete on storage, so orphans are expected.

Private is a leak-limiter, not a security boundary: the repo is public and the anon key ships in index.html, so anyone who goes looking can mint their own signed URLs. What it buys is that a proof URL which is forwarded, scraped or indexed stops working within the hour. Only real auth would make the photos genuinely private, and that would cost the "open the link, type your name" join flow.

The `chat_messages` migration is recorded separately in `supabase-chat.sql` (applied 2026-09-08) and the proof bucket in `supabase-proofs.sql` (applied 2026-09-08); `supabase-setup.sql` is not checked into the repo.

`supabase-setup.sql` is a **record of migrations already applied** to project `afxsoxexfahehhjijzlr`, not a script to run against a live DB. When you add a table or column, apply it as a migration and then append the SQL there with the same `-- Migration N: name (applied <date>)` comment style.

## Identity and state

There are no accounts. `me` is `{id, name, av, lat, lng, emoji, ...}` with a random `id` generated once and persisted to `localStorage` under `kansai-quest-me`; on reload, a saved name auto-rejoins via `startGame(true)`. Everything else is keyed by that `player_id` server-side, so "your" ticks and claims follow the saved id across sessions but not across cleared storage.

The pack checklist mirrors its state to `localStorage` under `kansai-quest-pack` as `{id, done[], pending[]}`, stamped with the `me.id` it belongs to and ignored if that no longer matches. A tick is applied to `ckDone` immediately and queued in `ckPending` until the server confirms it; a failed write keeps the tick and stays queued, retried by `ckFlush()` on the next Pack-tab open or the banner's "Retry now". `ckFetch()` replays the queue over the server's rows, so pending local edits win. This is the only feature that writes to `quest_claims` optimistically without rolling back.
